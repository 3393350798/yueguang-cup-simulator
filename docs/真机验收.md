# 两种真机链路的验收

双击 **scripts/field-acceptance.bat**，选择接线方案，导入同一轮录下的两份 CSV，检查并保存本地 JSON 报告。也可以先填一个预期动作编号，不导入日志，生成这一次的缺项清单。工具可生成空白 CSV 模板，兼容[实车录制与联调](实车录制与联调.md)已有的字段映射。它不打开相机或串口，不发送命令。

| 方案 | 第一份日志 | 第二份日志 |
| --- | --- | --- |
| OpenMV → STM32F103C8T6 直连 | OpenMV 自己的日志，或独立调试端口导出的板端日志 | STM32 同一次开机的日志 |
| 手机串流 → 电脑识别 → 无线串口 → STM32F103C8T6 | 电脑端的日志；到帧是电脑真正拿到一帧的时刻 | STM32 同一次开机的日志 |

## 两套接线都做同样的检查

1. **拍到画面。** 固定车和测试目标，先核对画面是否有目标或被遮挡。在程序实际拿到图像时记 `frame_received`；视觉程序完成自己的处理时记 `vision_done`。同一次动作的这两条和后面的指令应共用一个编号，例如 `test01`。记录“处理完成”不能证明识别正确；现场还要核对识别结果。
2. **发出且收到。** 先确认发送、接收端的波特率、串口设置和接线。OpenMV 用自己的发送记录，电脑用串口写入成功的记录，两者均记为 `command_sent`。STM32 只有在自己的程序**收到并解析该条指令**后才记 `command_received`。贯穿两端的编号需要出自队伍现有的协议或可核对的日志；无法可靠关联时不要手工补造。若协议有回执，可另记板端的 `reply_sent` 和电脑实际匹配到本次回执的 `reply_observed`。写串口成功只能证明本机写入成功。
3. **看左右轮响应。** 在轮子可自由转动、车体稳固的条件下，用队伍自己已经核对过的低速测试指令，先执行一次短动作并复核能停稳，再用不同编号重复。每次先在静止时记录一组已和该动作绑定的实测轮速，收到指令后继续记编号相同的双轮采样。现场另确认左右轮实际运动、方向和停稳；工具不根据 PWM 目标或目标速度判断实际运动。若无编码器记录，物理观察依然可用，但自动报告的轮速项应保留为未观测或缺少样本。
4. **验证变化后的恢复。** 在有条件安全停机时，用新编号重复一次。手机链路可断开串流再接回；直连链路可在静止时重启视觉端。恢复后重新跑上面的短动作，检查首帧、首条指令和双轮响应；设备重启后另起一份日志。这项是现场检查，报告不能从几条日志自动判断断流或重启是否真的发生。

各文件时间要来自**该设备自己的时钟**，且不倒退。事件须按发生顺序写入；时间戳相同的事件按日志行序核对。工具在同设备上统计取帧到识别、识别到发送，以及板端接收至轮速达阈值的间隔。电脑观察到回执时，电脑发送至见到回执的间隔包含板端处理；不能拆算无线单程、比较 OpenMV 与 STM32 的绝对时刻，也不能据此推算手机曝光时刻。

## 最小日志格式

上游（OpenMV 或电脑）使用以下列，下面只有演示行；真实验收需填自己的记录。

```csv
time_s,event,case_id
1.000,frame_received,test01
1.018,vision_done,test01
1.020,command_sent,test01
```

STM32 至少要能区分接收事件与硬件实测采样。用 `sample`、同一个 `case_id` 和下列轮速列表示静止及响应采样。单位 m/s；如果原日志是毫秒和 mm/s，可以分别用字段映射的 `time.unit: "ms"` 和对应信号的 `scale: 0.001`。

```csv
time_s,event,case_id,speed_left_m_s,speed_right_m_s
8.100,sample,test01,0.00,0.00
8.130,command_received,test01,,
8.155,sample,test01,0.02,0.02
8.180,sample,test01,0.06,0.05
```

默认以板端收到指令前后各 0.5 秒为板端观测窗口，以绝对轮速至少 0.03 m/s 为响应证据。如果前后还有其他板端接收记录，只使用上一条接收之后、下一条接收之前的样本，即使那些接收记录没有动作编号。与接收事件同一时刻的样本不用于判断前后；同一板端时刻、同一路轮速有冲突值会报错。验收时一次只跑一个动作，让车停稳，再取下一个编号。静止基线缺失、原本已经在动、没有有效样本、样本未达到阈值分别显示。响应记录只说明在有效窗口里观测到了轮速变化，方向、停车和动作的正确性仍由现场核对。

## 检查和留档

- 常规用法：打开窗口，给两个设备选各自的日志（缺一份也能看缺项）；成套日志需要相同的动作编号。日志来源可以标为「合成或仿真记录」或「提交者标注为实体记录」，默认为未标注。标注不等于工具验证过实体。
- 查看每个编号的首个缺项、顺序异常或重复事件，再看是否有更后面的独立证据。无事件或有歧义就补观测，别把没看到当作确定没发生。回执是可选项；只检查六个必看环节是否齐全，报告不判比赛是否通过。
- 保存前可先核对预览。报告只含标准事件、有限数值、来源角色和动作编号，不附原日志、路径、报文、固件或算法，不自动上传。动作编号建议用匿名短编号。若需画轮速波形，可按[实车录制与联调](实车录制与联调.md)导出单设备样本。

命令行也可以用来生成模板、检查证据和重复核对；报告文件不会覆盖已有文件。

```powershell
New-Item -ItemType Directory -Force -Path output
.\scripts\field-acceptance.bat template --profile openmv output\openmv-bench
# 用自己的记录填充模板后再运行：
.\scripts\field-acceptance.bat check --profile openmv --openmv output\openmv-bench\openmv.csv --stm32 output\openmv-bench\stm32.csv --case test01 --report output\openmv-report.json
.\scripts\field-acceptance.bat check --profile phone --pc output\pc.csv --stm32 output\stm32.csv --stm32-map output\board-map.json --case test01 --report output\phone-report.json
```

不传 `--case` 时检查文件中能识别的编号；要检查尚无日志的动作，或者长日志需要只检查其中几个编号，可以多次传入 `--case`。使用 `--require-complete` 时，若没有动作或尚有必看缺项，命令返回 2；输入或保存错误返回 1。
